# WalnutSeed Go 后端实施计划

> 状态：**计划稿，未开工**（本文档不含任何代码改动）
> 定位：`walnut-backend-go` 是与 Python / Java 并存的**第三份同契约实现**
> 范围：**P0–P5 全量对齐**，`module_ai` **不在首期范围**（该模块在 Python 端仍是未提交的在制品，不追移动靶）

## 0. 决策基线

| 项 | 决策 | 依据 |
|---|---|---|
| 项目定位 | 第三实现，独立库 `walnut_seed_go` | 与现有双后端架构同构，可增量交付、随时可停 |
| Web 框架 | **Gin v1.12.0**（实测版本） | 中间件链与现有 ASGI 顺序 1:1 可映射；`RouterGroup.Use` 对应 `route_class=OperationLogRoute` |
| ORM | **GORM v2** | 行级数据权限 + 动态列表筛选 + 逻辑删除，动态 `Where` 链最贴近 SQLAlchemy 写法 |
| 迁移 | **golang-migrate**，版本化 SQL | Schema 唯一事实源必须是 SQL；生产**严禁** `AutoMigrate` |
| Go 版本 | **1.26**（实测修正：原计划 1.24+ → 1.25+ → 1.26） | ⚠️ 依赖链决定：`gin v1.12.0` 要求 `go >= 1.25.0`，`go-redis v9.23.0` 要求 `go >= 1.26.0`。本机 Go 1.21 经 `GOTOOLCHAIN=auto` 自动拉取即可（见 §9.4） |
| 端口 | **8011**（与 Python/Java 相同） | 前端零改动，compose 互切 |
| 首期范围 | P0–P5，AI 模块除外 | 见上 |

### 0.1 三端并存的隔离约定（必须严格遵守）

| 维度 | Python | Java | **Go** |
|---|---|---|---|
| 数据库 | `walnut_seed_python` | `walnut_seed_java` | **`walnut_seed_go`** |
| Redis 键前缀 | `walnut-seed-python` | `walnut-seed-java` | **`walnut-seed-go`** |
| 日志文件名 | `walnut-seed-python.log` | `walnut-seed-java-*.log` | **`walnut-seed-go.log`** |
| 镜像名 | `walnut-seed-backend`（默认） | `walnut-seed-backend-java` | **`walnut-seed-backend-go`** |
| 容器名 | — | `walnut-backend-java` | **`walnut-backend-go`** |
| 迁移工具 | Alembic | Flyway | **golang-migrate** |

## 1. 现状基线（迁移的「源代码事实」）

### 1.1 表清单（17 张，全部需复刻）

```
sys_user            sys_user_role       sys_user_post
sys_role            sys_role_menu       sys_role_dept
sys_menu            sys_dept            sys_post
sys_dict_type       sys_dict_data       sys_config
sys_notice          sys_client          sys_social
sys_oper_log        sys_logininfor
```
排除（AI 模块，首期不做）：`ai_document`、`ai_document_chunk`、`ai_conversation`、`ai_message`

**权威来源**：`walnut-backend-python/app/alembic/versions/51e22ab7d9b4_init_schema.py`（17 个 `create_table`）。
Go 的 `migrations/0001_init_schema.up.sql` 必须与之**逐列、逐索引、逐约束对齐**，命名遵循 Python 端 `base_model.py` 的 `NAMING_CONVENTION`（`ix_*` / `uq_*` / `fk_*` / `ck_*`）。

### 1.2 路由面（组合根：`app/api/v1/router.py`）

| 挂载点 | 子路由 | 说明 |
|---|---|---|
| `/common` | HealthRouter、FileRouter | `/common/health`、`/common/health/*`、`/common/file/*` |
| `/`（根） | FileServeRouter | `GET /upload/{key}` 对象存储流式回源 |
| `/resource` | ResourceRouter | `/resource/sse`、`/resource/sse/close`、`/resource/websocket` |
| `/system` | Post、DictType、DictData、Config、Notice、Client、Dept、Menu、Role、**Profile、User** | ⚠️ Profile 必须先于 User 注册，否则 `/user/{userId}` 吞掉 `/user/profile` |
| `/system/social` | SocialRouter | 自带完整前缀 |
| `/monitor` | OperLogRouter、LogininforRouter | 自带完整前缀 |
| `/`（根） | AuthRouter | `/auth/login`、`/auth/logout`、`/auth/register`、`/auth/code`、`/auth/tenant/list` |
| `/`（根） | `GET /` index | 返回欢迎文案（纯字符串，非信封） |

> **Gin 侧对应坑**：Gin 的路由树是 httprouter 系，`/user/:userId` 与 `/user/profile` **会直接 panic**（通配符与静态段冲突），不像 FastAPI 靠注册顺序解决。
> **对策**：把 `profile` 作为静态路由显式注册，且 Gin 要求静态优先——实测 Gin 允许 `/user/profile` 与 `/user/:userId` 共存（静态段优先匹配），但**必须验证**；若冲突则改用 `/user/id/:userId` 并在 nginx/前端侧确认无影响，或统一用查询参数。**这是 P3 的第一个待验证项，不要假设。**

### 1.3 中间件链（外 → 内，顺序是隐式契约）

```
HTTPSRedirect(prod 且开关开启)
  → TrustedHost(prod)
    → CORS
      → Locale（Accept-Language）
        → ApiDecrypt（开关；密钥无效则不注册）
          → XSS（开关；/system/notice 排除）
            → RequestLog（记录的是解密后明文，且已脱敏）
              → GZip
                → CorrelationId
                  → 业务路由
```
> 顺序错误的后果：日志记到密文、XSS 过滤在解密前跑（等于没过滤）、trace id 缺失。**Gin 侧 `Use()` 的调用顺序即执行顺序**，与 Python 的「逆序叠加」相反，移植时不要照抄 `[::-1]` 逻辑。

### 1.4 认证白名单（`WHITE_API_LIST_PATH`，**17 条**）

```
/                     /auth/login         /auth/logout      /auth/register
/auth/code            /auth/tenant/list   /resource/sse/close
/resource/websocket   /common/health      /common/health/*  /upload/*
/static*              /web*               /docs*            /redoc
/openapi.json         /favicon.ico
```
Go 侧必须实现**启动期路由认证审计**（对应 `audit_routes_auth`）：遍历 `gin.Engine.Routes()`，白名单外若未挂认证中间件 → **启动失败（fail-fast）**。这是 Python 端已有的强安全约束，Go 不能降级。

### P1 · 基础设施内核 `规模 L`

| # | 任务 | 产出文件 | 验收标准 |
|---|---|---|---|
| 1.1 | **建库引导**（Go 驱动无 `createDatabaseIfNotExist`） | `internal/pkg/databasex/bootstrap.go` | `walnutctl migrate up` 能连到无库的 MySQL，执行 `CREATE DATABASE IF NOT EXISTS walnut_seed_go CHARACTER SET utf8mb4`，再跑迁移 |
| 1.2 | GORM 初始化 + 连接池 | `databasex/gorm.go` | `MaxOpenConns`/`MaxIdleConns`/`ConnMaxLifetime` 显式设置；`ConnMaxLifetime < MySQL wait_timeout`；`parseTime=true&loc=Local&charset=utf8mb4` |
| 1.3 | 迁移落地 | `migrations/0001_init_schema.{up,down}.sql` | 17 张表与 Alembic `51e22ab7d9b4` **逐列/索引/约束一致**；`down` 能干净回滚 |
| 1.4 | 种子数据 | `seed/mysql_data.sql`、`walnutctl seed` | 幂等；admin/admin123、pc 客户端、完整菜单/角色/字典与 Python 基线一致 |
| 1.5 | Redis 封装 | `cachex/` | **键前缀 `walnut-seed-go` 生效**；pub/sub 可用；连接健康检查 |
| 1.6 | **AES-ECB-PKCS7** | `cryptox/aes.go` | 手写逐块加密（Go stdlib 无 ECB）；密钥长度 16/24/32 校验；与 Python `encrypt_by_aes` **互通测试向量全绿** |
| 1.7 | **RSA-PKCS1v15 分段** | `cryptox/rsa.go` | 加密块 `keySize/8-11`、解密块 `keySize/8`；Base64 DER（私钥 PKCS#8 / 公钥 SPKI）；PEM 头容错剥离；**1024 位开发密钥在 Go 1.24 下实测可用** |
| 1.8 | bcrypt + JWT | `cryptox/bcrypt.go`、`jwt.go` | Go 能验 Python seed 的 admin 哈希；JWT HS256 claims 与 `security.py` 逐字段一致（含 `clientid`） |
| 1.9 | 中间件链（9 层，顺序即契约） | `internal/pkg/middleware/*`、`bootstrap/middleware.go` | 顺序与 §1.3 完全一致；ApiDecrypt 在 XSS/RequestLog **之前**；请求日志记录的是解密后明文 |
| 1.10 | 可信代理 + 客户端 IP | `netx/`、`middleware/trustedproxy.go` | **`r.SetTrustedProxies(cfg.TrustedProxyIPs)` 显式调用**；非可信来源不解析 XFF |

### 4.4 密码学互通向量（`test/cryptointerop/`）

- 长数据 RSA 分段：> `keySize/8-11` 字节的载荷双向可解

### 9.1 雪花 ID 与大整数序列化 —— ⚠️ 推翻原方案

**代码事实**（`app/common/response.py:26-32`）：

```python
_JS_SAFE_MAX = 9007199254740991
_JS_SAFE_MIN = -9007199254740991

def _encode_int(value: int) -> int | str:
    return value if _JS_SAFE_MIN < value < _JS_SAFE_MAX else str(value)
```

该规则经 `_JSON_CUSTOM_ENCODER` 作用于**响应中所有 int 字段**，不只是 ID。`bool` 因是 `int` 子类被单独优先匹配。

**实测边界**（严格不等式 → 边界值本身也转字符串）：

| 输入 | 输出 | 类型 |
|---|---|---|
| `0` / `1` / `-1` / `100` | 同值 | **数字** |
| `9007199254740990`（MAX−1） | 同值 | **数字** |
| `9007199254740991`（MAX 本身） | `'9007199254740991'` | **字符串** |
| `9007199254740992` | `'9007199254740992'` | 字符串 |
| `-9007199254740991`（MIN 本身） | `'-9007199254740991'` | **字符串** |

**雪花 ID 实测量级**（`app/utils/snowflake.py`，1+41+10+12 位，epoch 2020-01-01）：

```
样本：904941282285273088 / 904941282285273089 / 904941282285273090   （18 位）
JS_SAFE_MAX：9007199254740991                                       （16 位）
比值：100.5 倍  →  雪花 ID 恒定超出安全范围  →  恒定序列化为字符串
```

**Go 侧正确实现（不可用 `,string` tag）**：

```go
// JSInt 复刻 Python _encode_int 的条件转换语义
type JSInt int64

const jsSafeMax = 9007199254740991
const jsSafeMin = -9007199254740991

func (v JSInt) MarshalJSON() ([]byte, error) {
    n := int64(v)
    if n > jsSafeMin && n < jsSafeMax {   // 严格不等式，边界值转字符串
        return strconv.AppendInt(nil, n, 10), nil
    }
    return json.Marshal(strconv.FormatInt(n, 10))
}

// UnmarshalJSON 必须同时接受数字与字符串：
// 前端回传 ID 时是字符串（因为它收到的就是字符串），Pydantic 会强转，Go 不会
func (v *JSInt) UnmarshalJSON(data []byte) error {
    var n int64
    if err := json.Unmarshal(data, &n); err == nil {
        *v = JSInt(n)
        return nil
    }
    var s string
    if err := json.Unmarshal(data, &s); err != nil {
        return err
    }
    n, err := strconv.ParseInt(s, 10, 64)
    if err != nil {
        return err
    }
    *v = JSInt(n)
    return nil
}
```

**配套规则**（同一 `_JSON_CUSTOM_ENCODER` 内，需一并对齐）：
- `Decimal → str`（恒字符串）→ Go 用 `shopspring/decimal`，其默认 `MarshalJSON` 即输出带引号字符串，天然一致
- `datetime → DATETIME_DISPLAY_FMT`、`date → DATE_DISPLAY_FMT`、`time → TIME_DISPLAY_FMT` → Go 侧 `JSONTime`/`JSONDate`/`JSONTimeOnly` 三个类型，零值输出 `null`
- 该编码器作用于「未走 Pydantic 的 dict 等」裸值；走 Pydantic 模型的字段由模型自身序列化，**两条路径都要覆盖**，否则同一字段在不同端点表现不一致

> ⚠️ **P0 必须补一个用例**：构造 `{"status": 0, "id": <雪花>, "total": 5}` 的响应，断言输出为 `{"status":0,"id":"9049...","total":5}` —— status/total 是数字、id 是字符串。这一条能一次性防住整类回归。

### 9.2 加解密互通 —— ✅ 双向验证通过

**验证方法**：Python `cryptography` 生成测试向量 → Go 解密并**重新加密比对密文**；Go 生成密文 → Python 反向解密。

AES/ECB/PKCS7 是**确定性算法**（无随机填充），因此「密文逐字节相同」是比「能解开」强得多的判据——任何模式、填充、编码差异都会立刻暴露。

**结果**：

| 测试项 | 结果 |
|---|---|
| Go 解 Python 的 AES 密文 | ✅ **21/21** 一致 |
| **Go 加密结果 vs Python 密文逐字节比对** | ✅ **21/21 完全相同** |
| Go 解 Python 的 RSA 密文 | ✅ **5/5** 一致 |
| Python 解 Go 的 RSA 密文（反向） | ✅ **5/5** 一致 |
| RSA 密文分块均为 128 字节整数倍 | ✅ |
| 1024 位 RSA 在 Go 1.24.0 / 1.25.0 | ✅ 均正常（R1 解除） |
| AES-128/192/256 × {空串, 单字节, 整块 16B, 跨块 17B, JSON, 中文, 混排} | ✅ 全部往返一致 |
| PKCS7 整块补齐语义（16B 明文 → **32B** 密文） | ✅ 补满一整块，与 Python `PKCS7(128)` 一致 |
| 非法密钥长度拦截（非 16/24/32） | ✅ 报错文案与 `_check_aes_key` 一致 |

**确认的算法规格**（`app/core/encrypt.py`）：

| 项 | 规格 | Go 对应 |
|---|---|---|
| AES 模式 | `AES/ECB/PKCS5Padding`（即 PKCS7，块长 128 位） | **标准库无 ECB，必须手写逐块** |
| AES 密钥 | password 字符串 UTF-8 编码，长度须 16/24/32 | `aes.NewCipher([]byte(password))` |
| AES 输出 | Base64 标准编码 | `base64.StdEncoding` |
| RSA 填充 | `RSA/ECB/PKCS1Padding` → **PKCS1v15**（非 OAEP） | `rsa.EncryptPKCS1v15` / `rsa.DecryptPKCS1v15(rand.Reader, ...)` |
| RSA 密钥格式 | Base64 编码 DER：公钥 X.509/SPKI，私钥 PKCS#8 | `x509.ParsePKIXPublicKey` / `x509.ParsePKCS8PrivateKey` |
| RSA 加密分段 | `max_chunk = key_size//8 - 11`（1024 位 → **117 字节**） | `pub.Size() - 11` |
| RSA 解密分段 | `chunk_size = key_size//8`（1024 位 → **128 字节**） | `priv.Size()` |
| 空输入 | `chunks = [...] or [b""]` → 按**一个空块**处理 | 需显式分支 |
| 一次性 AES 密钥 | `random_string(32)`，字符集 `a-z0-9`（36 字符） | 同字符集 |

**两个必须复刻的实现细节**：

1. **多字节字符切断**：Python 对 **UTF-8 字节流**分段（`raw[i:i+max_chunk]`），会把中文等多字节字符从中间切断。解密时**先拼接全部解密字节，最后才 `.decode("utf-8")`**。Go 必须同样先 `append` 拼完再 `string(out)`——若逐块 `string()` 再拼接会产生非法 UTF-8。已用 396 字节含中文载荷（约 4 块）验证还原一致。
2. **PKCS1v15 的 `-11` 是填充特征**：OAEP 是 `-42`。分段参数取 `-11` 本身就证明了对端是 PKCS1v15，Go 侧不可误用 `EncryptOAEP`。

> §9.2 的 `encryptByAES` / `decryptByAES` / `encryptByRSA` / `decryptByRSA` 四个函数已通过逐字节互通验证，可**直接作为 `internal/pkg/cryptox/` 的实现起点**，无需重写。

### 9.3 Gin 路由行为 —— ✅ 无冲突，但发现尾斜杠差异

> **双版本复验**：以下全部结论在 **gin v1.12.0（Go 1.25.0）** 与 **gin v1.10.0（Go 1.25.0）** 上**逐项一致**。
> 仓库现有骨架 `walnut-backend-go/go.mod` 钉的是 `gin v1.10.0` + `go 1.21`，故结论直接适用。

**场景 1：同层静态段与参数段共存**

| 注册顺序 | 是否 panic | `GET /user/profile` | `GET /user/{雪花ID}` |
|---|---|---|---|
| 静态优先（profile 先） | 否 | `STATIC-profile` ✅ | `PARAM-userId` ✅ |
| **参数优先（:userId 先）** | 否 | `STATIC-profile` ✅ | `PARAM-userId` ✅ |

→ **Gin 的静态段恒优先，与注册顺序无关。**

**对照 FastAPI 实测**（颠倒 `router.py` 的注册顺序，即 `:userId` 先注册）：

```
GET /system/user/profile          -> HTTP 200 {'hit': 'PARAM', 'userId': 'profile'}   ← 被吞掉
GET /system/user/1948234567890123456 -> HTTP 200 {'hit': 'PARAM', ...}
```

→ **FastAPI 确实依赖注册顺序**，这正是 `router.py` 里「Profile 须先于 User 注册」注释的由来。
→ **Go 侧该约束自动消失**，移植时不必复刻顺序依赖（但保留顺序也无害）。

**场景 2：全量真实路由集**

注册 Python 端 user + profile 的**全部 21 个端点**（含 `/user/list`、`/user/list/dept/:deptId`、`/user/authRole` PUT 与 `/user/authRole/:userId` GET 同层混排、`DELETE /user/:userIds` 与 `GET /user/:userId` 参数名不同）：

- ✅ **注册成功，无 panic，共 21 条路由**
- ✅ **18/18 端点匹配正确**，无一被 `:param` 误吞

> 注：`DELETE /user/:userIds` 与 `GET /user/:userId` 参数名不同却不冲突——Gin 每个 HTTP 方法有独立路由树。

**场景 3：⚠️ 尾斜杠重定向语义差异（新发现 R16）**

前端 `apps/web-antd/src/api/system/user/index.ts:17` 定义 `root = '/system/user'`，**无尾斜杠**；而 Python 端注册的是 `/system/user/`（带尾斜杠）。两端都会重定向，但**状态码不同**：

| 请求（缺失尾斜杠） | FastAPI/Starlette | Gin v1.12 |
|---|---|---|
| `GET /system/user` | **307** | **301** ⚠️ |
| `POST /system/user` | **307** | **307** |
| `PUT /system/user` | **307** | **307** |

Gin 的实现是：GET/HEAD → `301 Moved Permanently`，其他方法 → `307 Temporary Redirect`。

**影响评估**：
- **POST/PUT 安全**：307 保留方法与请求体，与 Starlette 一致。实测 `POST /system/user`（无尾斜杠）经重定向后 body、`Authorization`、`encrypt-key` 头**全部完整送达** handler。原担心的「301 丢 body / 降级成 GET」**不成立**。
- **GET 有隐患**：301 是**永久重定向，会被浏览器与中间代理缓存**。若日后 Go 侧改为直接注册 `/system/user`，已缓存 301 的客户端仍会绕道 `/system/user/`，故障长期滞留且难排查。

**实测可行的三种解法**：

| 方案 | 做法 | 实测结果 |
|---|---|---|
| **① 推荐** | 注册**前端实际使用的无尾斜杠形式**（`u.POST("")` 而非 `u.POST("/")`） | `POST /system/user` → **HTTP 200 直达**，body 与全部自定义头完整 |
| ② 最稳 | 两种形式都注册指向同一 handler + `engine.RedirectTrailingSlash = false` | `/system/user` 与 `/system/user/` **均 200 直达**；未注册路径干净返回 **404**（不再 301） |
| ③ 对齐 | 保留 Gin 默认，但契约 diff 跑分器统一「跟随重定向后比对最终响应」 | 最终响应一致，但 GET 的 301 缓存隐患仍在 |

**建议采用 ②**：彻底消除重定向，两种 URL 形式都直达 200，且不依赖客户端的重定向跟随行为。代价是每个「根路径」端点注册两次——可在 `bootstrap/router.go` 用一个 helper 统一处理，避免散落。

### 9.4 Go 环境可用配方 —— ⚠️ 修正原计划

原计划建议 `GOPROXY=https://goproxy.cn,direct`。**实测该配方在本机不可用**：

| 源 | 实测结果 |
|---|---|
| `goproxy.cn` | ❌ `curl: (35) Recv failure: Connection was reset`（0.39s） |
| `goproxy.io` | ❌ `curl: (35) Recv failure: Connection was reset`（0.23s） |
| `sum.golang.google.cn` | ❌ `wsarecv: An existing connection was forcibly closed`（120.232.233.171） |
| `proxy.golang.org` | ⚠️ 小请求可通（200/815ms），但**大文件超时**（工具链 zip 拉取失败） |
| **`mirrors.aliyun.com/goproxy`** | ✅ **200 / 1.14s，直连无需代理** |
| SOCKS5(1080) → `proxy.golang.org` | ✅ 200（备用路径） |

**可用配方**：

```bat
set GOPROXY=https://mirrors.aliyun.com/goproxy/,direct
set GOSUMDB=sum.golang.org
set GOTOOLCHAIN=auto
```

**三个关键点（均已踩坑验证）**：

1. **`GOSUMDB` 必须保持默认值 `sum.golang.org`，不要改成 `sum.golang.google.cn`。**
   显式设置会让 Go **绕过代理直连**该主机（已实测被重置）。保持默认时，Go 会把 sumdb 查询**经 GOPROXY 转发**（阿里云镜像支持 sumdb 代理），反而能通。
2. **不要用 `GOSUMDB=off`。** 工具链模块（`golang.org/toolchain`）的校验**强制要求** sumdb，关掉后报错 `verifying module: checksum database disabled by GOSUMDB=off`，连已缓存的工具链都无法使用。
3. **`GOTOOLCHAIN=auto` 可跨版本自动拉取。** 本机 Go 1.21.0，因 `gin v1.12.0` 要求 `go >= 1.25.0`，自动下载并切换到 **go1.25.0** 后编译通过。

**落地建议**：
- 仓库内提供 `.go-version` 钉 `1.25.x`；README 的 Go 快速开始写明上述三行配方
- `Dockerfile` 用 `ARG GOPROXY=https://mirrors.aliyun.com/goproxy/,direct` 并把 `go mod download` 单独成层做缓存（对齐 commit `72534a5` 的前端构建缓存思路）
- CI 环境若在海外，直接用默认 `proxy.golang.org` 即可，配方可用 `GOPROXY` 构建参数覆盖

#### 发现①：`module_ai` 根本没挂载，因此不在契约内

### 11.6 路由清单 diff 已落地（计划 §4.1）

`test/contract/routes_inventory_test.go` 把 Go 的路由面与 `routes.txt` 对比，
**纯静态、无需启动服务，可进每次 CI**。两个方向的语义刻意不对称：

| 方向 | 处理 | 理由 |
|---|---|---|
| Go 有、Python 没有 | **硬失败** | 私自新增接口就是契约漂移，必须挡住 |
| Go 没有、Python 有 | P0–P2 报告覆盖率；**P3 起转硬失败** | 迁移是增量的，未完成的路由不该让 CI 一直红 |

路径归一化处理了三类实测差异（都不是推测，均来自 `routes.txt` 真实内容）：

```
{user_id}          → :user_id
{user_id:int}      → :user_id       Python 用路径转换器限定类型，Gin 无此机制
{file_path:path}   → *file_path     Python 的 path 转换器允许含斜杠，对应 Gin catch-all
```

- 把 `.env.test` 的 `VITE_GLOB_ENABLE_ENCRYPT` 改为 `false`（与 production 对齐，最省事）

### 13.4 关键实现决策

**① `grant_type` 校验是字符串子串匹配，不是列表成员判断**

Python 端写的是 `body.grant_type not in (client.grant_type or "")`，
而 `client.grant_type` 存的是逗号分隔串（如 `"password,social"`），
所以 `in` 做的是**子串包含**判断。

Go 侧照抄 `strings.Contains(grantTypes, body.GrantType)`。
若"修正"成 split 后精确匹配，行为会与另两端不同
（例如 `grant_type="pass"` 在 Python 端能通过、在 Go 端不能）——
这是既有的宽松实现，**契约一致性优先于代码正确性**。已在 handler 里注释说明。

**② 限流 fail-closed**

Redis 不可用时**拒绝**请求而非放行（返回"服务器限流异常，请稍候再试"），
与 Python 端 `except → raise ServiceException` 一致。限流是安全控制，
缓存挂了就放行等于把它形同虚设。

**③ 登录失败计数的键是「用户名 + IP」**

不是只按用户名。否则攻击者可以用错误密码把任意账号锁死（拒绝服务）。
且「用户不存在」与「密码错误」走**同一条计数路径、同一错误码、同一文案**（防账号枚举）。

**④ 验证码 uuid 用 crypto/rand**

`idgen.UUID()`（等价 Python 的 `uuid.uuid4().hex`）。
⚠️ 不能用 `math/rand`：uuid 是验证码在 Redis 里的唯一凭据，
可预测就意味着攻击者能枚举/复用他人的验证码，绕过整个验证码机制。

**⑤ 验证码比对大小写不敏感**

Python 端用 `equals_ignore_case`。若 Go 改成区分大小写，
char 模式下用户输入 `ab12` 而答案是 `AB12` 就会失败——同一前端在两个后端上表现不同。

**⑥ `RouteBinder` 用函数结构体而非接口**

`bootstrap` 依赖 `auth`（注册路由），`auth` 不能反向依赖 `bootstrap`（成环）。
而接口方案也走不通：`bootstrap.Group.GET` 返回 `*Group` 支持链式调用，
Go **不允许**把有返回值的函数赋给无返回值的函数类型，接口签名必须完全一致。
故用 `RouteBinder{GET, POST func(...)}`，由 bootstrap 侧闭包适配丢弃返回值。

### 13.5 已知偏差（已接受，均有测试覆盖）

| 项 | 说明 |
|---|---|
| **JWT header 键序** | PyJWT 输出 `{"typ":"JWT","alg":"HS256"}`，golang-jwt 输出 `{"alg":"HS256","typ":"JWT"}`。故同一 payload 两端签出的 token 字符串不同，但**互相可验证**（header 自描述）。三端 token 本就不要求可互换（各自独立 Redis 会话）。`diff_auth.py` 只比对 `alg` 值，不比对 header 字节 |

| **验证码图片字节** | 随机图片不可能逐字节相同，`diff_auth.py` 把 `img` 归一化为 `<IMG>`，只验证字段存在与非空 |

**⚠️ 首版比对方法本身是错的**：一开始用 `mysqldump` 文本 / `SHOW CREATE TABLE` 对比，
报出 **216 行差异**，看起来像是迁移写错了。实际排查发现两库的

### 14.4 关键实现决策

**① `authctx` 必须是 `pkg` 下的叶子包，不能定义在 `auth` 里**

认证中间件（`module/web/auth`）**产出**上下文，业务模块（`module/system/user`、`menu`…）
**消费**它。若类型定义在 auth 包，业务模块就要反向依赖 web 层，
而 auth 包本身又 import middleware —— 很快绕出导入环。
故独立成 `pkg/authctx`，两侧都只依赖这个不含业务语义的包。

**② `routex.Binder` 用「函数类型的结构体」，不是接口**

两个原因，第二个是硬约束：
- 业务模块不能 import bootstrap（bootstrap 要 import 它们才能装配路由）
- 接口也不行：`bootstrap.Group.GET` 的签名是
  `func(string, ...gin.HandlerFunc) *Group`（返回自身支持链式），
  而 Go **不允许**把有返回值的函数赋给无返回值的函数类型，接口方法签名必须完全一致

故由 bootstrap 侧用闭包适配丢弃返回值（`Group.Binder()`）。
附带好处：handler 能脱离 bootstrap 做单元测试。

**③ `authMiddleware` 必须在 `registerRoutes` 之前注入**

`Protected()` 组在**创建时**就把当时的 `authMiddleware` 快照进 gin 的 handler 链，
之后再改字段不会生效。这是个静默失效陷阱——路由看起来注册成功、
审计也通过（审计只看登记表），但实际不带认证。已在 `buildEngine` 里固定顺序并加注释。

**④ 权限从会话快照取，不查库**

`authctx.Context` 的 `Permissions` / `Roles` / `MenuIDs` 三个集合字段
全部由 Redis 会话快照（`menu_permission` / `role_permission` / `menu_ids`）填充。
这是 Python 端的既有设计：权限在登录时算好缓存进会话，每次请求只做一次 Redis 读，
**改权限后需重新登录才生效**。两端行为一致，不要在 Go 侧"优化"成实时查库。

**⑤ 建树时 `parent_id IS NULL` 的菜单必须跳过**

Python 端把它归到字典的 `None` 键下，而 `_build_children` 只用整数 `parent_id` 查找，
`None` 键永远取不到 —— 等价于丢弃。若在 Go 里用 `ParentIDOrZero()` 之类写法把 NULL 当 0，
会凭空多出一批顶级路由。这是 §14.3 第 7 组能做**严格逐字节**比对才敢确认的细节。

**⑥ `getInfo` 刻意忽略数据权限**

查的是当前登录用户自己，不需要行级过滤；其依赖是 `get_current_user` 而非 `AuthPermission`。
`getRouters` 同理 —— 只要登录就能取自己的路由，否则普通用户登录后主页空白。

**⑦ nil slice 兜底已在两处落地**

`GetRouters` 与 `getInfo` 的 `roles` 都保证输出 `[]` 而非 `null`
（Python 端列表推导的结果本就是 `[]`）。前端 `routers.forEach` 才不会崩。
